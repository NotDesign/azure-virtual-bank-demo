# 開發接手的狀態與授權約定

## 歸屬與讀取

- session 必須由正式後端驗證。瀏覽器傳入的 role、owner、parent、customerId 不能成為正式授權依據。
- HQ 全域；L1 只含自己的分支；L2 只含自己的客戶；客戶只含本人。路由、查詢、直接 ID、匯出、變更、檔案讀取都須由伺服器各自檢查。
- 公開申請的邀請歸屬應在首次建立時由伺服器決定並固定。後續另開邀請不能換掉原 owner。
- 交易分潤使用交易發生時的 owner／價目／底價／比例快照；改價與移轉不能追溯改寫歷史。
- 全權帳號看客戶 eBanking 必須記錄實際操作人與代看客戶；正式版另需審計與操作限制。

## 申請版本與文件

- 每次提交或審核變更使用 applicationId＋revision。伺服器須在交易中比對版本及合法狀態，拒絕舊寫入。
- 補件回同一 applicationId，保留原歸屬與審核歷史；重認證與最終同意不能從草稿自動變成完成。
- 本機原件是 Blob；正式版改成受控文件儲存與授權下載。不可將永久公開 URL 當文件權限。
- 外審只分享白名單快照；原型的 SHA256 是一致性檢查，不是可信的伺服器簽章。

## 渠道狀態

資料補錄 → 合規審核 → 董事驗證 → 渠道審核中 → 渠道審核通過 → 戶口開通。

- 要求補件回「待補件」，補交後回 CS 補錄／重審。
- 駁回是獨立結果，須保留理由；不能當成已開戶。
- 正式銀行開通回覆應有渠道事件 ID、驗簽、重送去重及交易一致性。原型的「模擬開通」不代表銀行成功。
- 外審 token 應由後端驗證有效期、單案、渠道／審核員、版本、撤銷及使用狀態。正式審單結果應記錄人員、時間、理由、文件要求與決策事件 ID。

本文件是工程接手約定，並非已實作的 OpenAPI 或正式合規認證。
